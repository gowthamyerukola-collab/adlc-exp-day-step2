**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
  - [CRITICAL] You MUST explicitly reference and implement the exact dual-plane C# startup, try-catch, and fallback logic blocks detailed at: `./docs/azure-cosmos-reference.md`.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** The implementation must stay inside `src/backend` and `src/frontend`. `src/backend/OuterloopLabApi.sln` is the required .NET solution entrypoint for build and test. `src/backend/Program.cs` must own the startup path that binds environment variables, runs the required Cosmos dual-plane provisioning flow from `docs/azure-cosmos-reference.md`, and registers the currency conversion feature services. Backend HTTP surface area should be added under exact paths in `src/backend` (for example, `Controllers`, `Endpoints`, `Services`, `Models`, or equivalent standard .NET files under that folder); if those files do not exist yet, create them under `src/backend` rather than outside it. On the frontend, `src/frontend/index.html` must carry the `__VITE_API_URL__` placeholder, and the user workflow should be implemented from `src/frontend/src/` with the main screen assumed to be rooted from `src/frontend/src/App.tsx` and bootstrapped by `src/frontend/src/main.tsx` unless the current app structure already uses an equivalent file in that same folder. `docs/azure-cosmos-reference.md` and `docs/CONTAINER_ENVIRONMENT_VARIABLES.md` are mandatory references for startup and configuration behavior.

**In Scope:**
- Add a backend API in `src/backend` that accepts a currency conversion request with source currency, target currency, and amount, fetches the latest rate from the external provider, calculates the converted amount, and returns a response that includes an audit record identifier.
- Persist one Cosmos DB audit record per successful conversion containing the request values, the normalized provider rate used for the calculation, the provider date or marker if supplied, and the exact backend-generated execution timestamp.
- Add a backend API in `src/backend` to retrieve a previously stored conversion audit record by identifier so an auditor or analyst can reconstruct the original conversion later.
- Add frontend UI in `src/frontend/src/` for entering amount/source currency/target currency, submitting the conversion request, showing the converted amount immediately, and displaying the generated audit identifier and timestamps returned by the backend.
- Add frontend UI in `src/frontend/src/` for looking up a prior conversion by audit identifier and rendering the stored rate, currencies, amount, converted amount, provider date/marker, and backend execution timestamp.
- Add automated tests under `src/backend` and `src/frontend` as appropriate for conversion calculation mapping, provider-schema adaptation, graceful upstream-failure handling, and audit retrieval behavior.

**Out of Scope:**
- User authentication, authorization, role management, or per-user audit partitioning.
- Batch conversion uploads, CSV import/export, or bulk reconciliation workflows.
- Historical trend charts, dashboards, or analytics beyond the single-conversion audit retrieval workflow.
- Manual override of provider rates or editing/deleting previously stored audit records.
- Infrastructure creation outside the application startup behavior already mandated in Known Constraints.
- Any caching layer, background polling job, or rate-refresh scheduler unless it is strictly required to satisfy an in-scope acceptance check.

**Feature Constraints:**
- Use `IHttpClientFactory` in `src/backend` for the external currency provider client so outbound calls are centrally configured and testable.
- Normalize currency codes to uppercase 3-letter ISO-style strings before calling the provider or storing the audit record; reject invalid or identical source/target currency pairs with a 400-level validation response.
- Use `decimal` for amount, rate, and converted amount values in backend models and persistence to avoid floating-point rounding drift in regulated financial calculations.
- Isolate external provider parsing behind a backend abstraction that can map multiple likely JSON shapes into one internal rate result model, including support for alternate property names such as `rates` or `conversion_rates` without leaking provider schema details into controllers or persistence models.
- Persist a non-expiring audit document shape that includes at minimum: audit record id, source currency, target currency, original amount, provider rate, converted amount, provider date or marker, backend execution timestamp, and provider source URL used for the request.
- If the upstream provider request fails, times out, or returns an unreadable payload, return `application/problem+json` with HTTP 503 and a domain-specific title such as `Currency rate provider unavailable`; do not persist a partial audit record for that failed request.
- Keep the frontend implementation dependency-light: use native React/Vite capabilities and the platform fetch API unless an existing dependency already in `src/frontend` is necessary; do not introduce a heavyweight state-management library for this feature alone.

**Expected Outcome:** A user can open the UI in `src/frontend`, enter a request such as `amount=100.00`, `from=USD`, `to=EUR`, submit it, and receive a successful response rendered on screen showing a concrete result such as `convertedAmount=92.00`, `providerRate=0.92`, `providerDate=2026-08-01`, `executedAtUtc=2026-08-01T12:34:56.789Z`, and an `auditId` generated by the backend. That same `auditId` can then be submitted to the audit lookup workflow and the application must return the exact stored record values, not a recomputed value from a fresh provider call. If the external provider is unavailable, the conversion API must return a `ProblemDetails` response with status `503` and a clear domain message, and the lookup for that failed attempt must not exist because no audit record was written. Validation failures such as `from=USD` and `to=USD` or a non-positive amount must produce a 400-level response instead of calling the provider.
