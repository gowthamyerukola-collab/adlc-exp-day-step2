**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the token-based Managed Identity credentials for authentication.  
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - [CRITICAL] You MUST explicitly reference to implement the C# startup, detailed at: `./docs/AZURE_COSMOS_REFERENCE.md`.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** Implementation should be confined to `src/backend/OuterloopLabApi.sln`, `src/backend/Program.cs`, the `net10.0` backend project that is added to that solution (assumption if a new project path is needed: `src/backend/OuterloopLabApi/OuterloopLabApi.csproj`), `src/frontend/index.html`, `src/frontend/package.json`, `src/frontend/src/main.tsx`, `src/frontend/src/App.tsx`, and a frontend runtime placeholder replacement script under `src/frontend` (assumption if one must be created: `src/frontend/entrypoint.sh`). The backend work should introduce explicit API surface area for conversion submission and audit retrieval under `src/backend`, and the frontend work should render a conversion form plus an audit lookup/history experience under `src/frontend` using the runtime-injected `VITE_API_URL`.

**In Scope:**
- Add a backend HTTP endpoint to submit a currency conversion request with a positive amount, a 3-letter source currency code, and a 3-letter target currency code.
- Call the configured external currency provider through a backend abstraction, normalize the provider response into an internal rate/result model, and compute the converted amount server-side.
- Persist one audit record per successful conversion in Cosmos DB with enough information to reconstruct the event later, including request values, applied rate, converted amount, provider marker(s), and the backend execution timestamp.
- Add backend HTTP endpoint(s) to retrieve a stored conversion by its audit identifier and to list recent conversion audit records in reverse chronological order.
- Add a React UI in `src/frontend` that lets the user enter the amount/from/to currencies, submit the conversion, see the returned rate and timestamp immediately, and browse or re-open recent audit records.
- Add automated backend tests for provider response normalization, request validation, successful audit persistence mapping, and graceful upstream failure handling.

**Out of Scope:**
- Caching or prefetching exchange rates.
- Multiple third-party providers, provider failover, or dynamic provider selection.
- Editing, deleting, or backfilling historical audit records.
- CSV, PDF, or email export workflows for auditors.
- User authentication, role management, or tenant isolation changes beyond the existing application setup.
- Bulk conversion uploads or scheduled/background conversion jobs.

**Feature Constraints:**
- Use `IHttpClientFactory` for outbound rate-provider calls so timeout and retry behavior can be configured centrally without coupling controllers/endpoints to raw `HttpClient` construction.
- Model monetary fields as `decimal` in the backend; do not use `double` or `float` for requested amount, applied rate, or converted amount.
- Validate currency codes as uppercase ISO-4217-style 3-letter strings and reject zero or negative amounts with a `400` `ProblemDetails` response.
- Expose a create endpoint at `POST /api/conversions` and retrieval endpoints at `GET /api/conversions/{id}` and `GET /api/conversions?limit=<n>` unless an existing route prefix in `src/backend/Program.cs` requires the same handlers under a versioned group; if so, preserve the group prefix and keep the same resource names.
- Persist both the provider's date/sequence marker and the backend-generated execution timestamp in UTC with sub-second precision on every successful audit record.
- Normalize external provider payloads behind an internal interface or mapper so the rest of the application reads a stable internal contract even if the upstream JSON uses different property names.
- Return a `503` `ProblemDetails` response titled `Currency rate provider unavailable` when the upstream provider cannot supply a usable rate, and do not leak raw exception text, stack traces, or serializer details in the response body.
- Display recent audit records newest-first in the frontend and allow selecting a record to re-display its stored amount, rate, converted amount, provider marker, and execution timestamp without recomputing it.

**Expected Outcome:** A treasury analyst can open the React UI, enter a request such as amount `100.00`, from `USD`, to `EUR`, submit it, and receive a response sourced from the backend that includes a stored audit identifier plus fields equivalent to: requested amount `100.00`, source currency `USD`, target currency `EUR`, applied rate `0.9200`, converted amount `92.0000`, provider date/marker `2026-08-01`, and backend execution timestamp `2026-08-01T14:03:22.481Z`. If the user later requests that audit record by its identifier, the backend returns the same persisted values rather than recomputing from the current market rate. If the provider call fails or returns an unusable payload, `POST /api/conversions` returns `application/problem+json` with HTTP `503`, title `Currency rate provider unavailable`, and no raw network or serialization error text.
